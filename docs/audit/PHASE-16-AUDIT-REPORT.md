## 1. Executive summary

UIL4B is in good structural health. Build is clean, lint is at baseline
(0 errors / 34 pre-existing warnings), routing is generated from a single
tool-tree source so surfaces can't drift, and the Create surface ships a real,
working tool suite. The audit did **not** find data-loss or security-critical
defects in the reviewed client paths.

What it *did* find — and what makes the app read as "AI-built" rather than
"team-built" — is **surface polish inconsistency**, concentrated in one place:

> **The single highest-leverage fix is the button system.** The codebase has one
> canonical button primitive (`.btn`) used **332 times across 50 files**, and
> **54 bespoke `*-btn` selectors** that each re-invent padding, radius, weight
> and colour. That is the mechanical root cause of "multiple button types" and
> "inconsistent padding" — it is measurable, and it is fixable without a rewrite.

The three big *product* gaps are strategic, not bugs: **Discover** and **Learn**
are honest coming-soon shells (only the Gradient Gallery is live), and the
**community backend** needs a design decision before build. Those are flagged for
you, not silently touched.

## 6. Systemic — needs your review

This is the section to read carefully. Each item changes how the app *scales*
or *feels*, so it's yours to approve before it lands wholesale.

### 6.1 ⭐ Flagship — the button / spacing system

**This is your "big red flag," quantified.**

- **One primitive, used everywhere it should be:** `.btn` (+ `.btn-s`, `.btn-l`,
  `.btn-accent`/`.btn-primary`, `.btn.is-loading`) appears **332× across 50
  files** [code]. This is already the house standard.
- **…and 54 bespoke `*-btn` selectors that bypass it** [code], each re-declaring
  its own padding, radius, weight and colour. That divergence is exactly what
  reads as "multiple button styles."

**Measured variance across a sample of the bespoke buttons** [code]:

| Class | padding | border-radius |
|---|---|---|
| `.btn` *(canonical)* | `10px 22px` | `--radius-pill` |
| `.btn-s` *(canonical)* | `6px 12px` | *(inherits pill)* |
| `.adm-time-btn` | `5px 12px` | `--radius-xs` |
| `.ch-sort-btn` | `5px 14px` | `--radius-pill` |
| `.topbar-icon-btn` | `7px` | `--radius-s` |
| `.stc-copy-btn` | `7px 14px` | `--radius-s` |
| `.topbar-btn-export` | `8px 12px` | `--radius-pill` |
| `.aipg-mode-btn` | `8px 16px` | `--radius-s` |
| `.cs-seg-btn` | `8px 16px` | `--radius-pill` |
| `.plb-pvb-btn` | `9px 18px` | `9px` *(hardcoded)* |
| `.ggn-btn` | `9px 18px` | `--radius-pill` |
| `.sidebar-login-btn` | `10px` | `--radius-pill` |
| `.arc-select-btn` | `10px 12px` | `--radius-s` |
| `.icust-proj-btn` | `10px 14px` | `--radius-lg` |
| `.global-feedback-btn` | `10px 16px` | `99px` *(hardcoded)* |
| `.lib-switch-btn` | `.24em .68em` | `--radius-pill` |

That's **~11 distinct paddings**, **6 different radii** (including two hardcoded
pixel values that ignore the token scale), and font-weights spanning 500/560/600/
700 — for what the user reads as "the same button." No amount of individual
tweaking fixes this; the *system* has to be unified.

**Recommended migration (the systemic decision to approve):**

1. **Adopt a strict button contract.** Every button is `.btn` + exactly one size
   (`.btn-s` / *(default)* / `.btn-l`) + one variant (`.btn-accent`,
   `.btn-ghost`, `.btn-icon`, `.btn-seg`). Radius, transition and focus ring come
   from the primitive — never re-declared.
2. **Introduce the two missing modifiers** the bespoke set actually needs:
   `.btn-icon` (square icon buttons — folds `.topbar-icon-btn`, `.pnav-icon-btn`,
   `.adm-eye-btn`, avatar buttons) and `.btn-seg` (segmented toggles — folds
   `.cs-seg-btn`, `.tt-seg-btn`, `.pnav-seg-btn`, `.ggn-seg-btn`, `.prev-seg-btn`).
3. **Fold the rest onto `.btn` + size** in reviewable batches, one feature area
   per commit (topbar → palette → gradient → admin → discover → misc), visual-
   diffing each. Delete the bespoke rule once its call-sites move.
4. **Kill the hardcoded radii** (`9px`, `99px`) as part of the fold.
5. **🔒 Flag, do not touch: `.auth-google-btn`.** It sits in the Human
   Validation Zone (Google sign-in). It stays visually as-is unless you
   explicitly approve a change to auth UI.

**Payoff:** one line changes button feel app-wide; padding/radius become
impossible to get wrong; the CSS shrinks. This is the change that most makes the
app "feel built by a team."

### 6.2 Spacing & breakpoint scale (D1)

Ad-hoc breakpoints and raw pixel paddings are scattered through `global.css`
[code]. Recommend naming the breakpoint scale (e.g. `--bp-sm/md/lg/xl`) and
routing component padding through the existing `--s-*` spacing tokens, the same
way buttons route through `.btn`. Same principle, wider surface.

### 6.3 Motion tokens (E2/E3)

The motion tokens (`--dur-1…6`, `--ease-out/-inout/-spring`) **are** defined
(`:root`, global.css ~line 4399) [code] — no bug — but inline `.2s`/`.3s`
durations still exist alongside them. Recommend migrating inline durations to the
tokens and adding one reduced-motion-safe success motion on export/copy/save, so
confirmation feedback is consistent.

### 6.4 The "finished-app" details AI usually skips

- **Branded 404** instead of `* → /` redirect (§5.5).
- **Offline handling** — a single app-level offline signal (§5.4).
- **Consistent empty states** as composed "getting started" views across
  Discover, Community, Projects.

### 6.5 Product surface strategy (flagged — your call)

- **Discover build-out:** only Gradient Gallery is live; Inspiration, Community
  Fonts/Prompts, Curated, Collections are shells. Sequencing is a product call.
- **Learn content:** routes + metadata exist; the articles are the work.
- **🔒 Community publishing backend:** media at scale needs a real backend and a
  design decision before build (also constrained by the Vercel 12-function
  ceiling — 11 used, 1 free). Escalated, not started.
- **🔒 Stripe retention/coupon config:** code is ready; the coupon + Customer-
  Portal cancellation are manual dashboard steps (owner-gated).
